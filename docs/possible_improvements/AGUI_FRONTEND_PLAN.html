AG-UI Bridge + Next.js Frontend

Plan to expose the FinSight A2A orchestrator over the AG-UI protocol and build a production-grade Next.js frontend on top, with full feature parity to adk web.

Decisions locked in (from this session):
  • Bridge mode: Augment — add a new endpoint that drives the orchestrator through its A2A JSON-RPC interface, leaving the existing /agentic_chat (Runner-backed, used by RAGAS evaluation) untouched.
  • Frontend stack: Next.js 16 + CopilotKit (@copilotkit/react-core, @copilotkit/react-ui, @copilotkit/runtime) talking AG-UI to the Python bridge.
  • Feature floor: every capability currently exposed by adk web (sessions, memory, event trace, tool inspection, multi-turn replay) must be available in the new UI before it can replace it.

Part A — A2A → AG-UI bridge

1. Current state

The orchestrator (agent_1_adk/main.py) already exposes three route groups on port 8001:

  • /a2a — A2A JSON-RPC, used by SubAgentClient and external A2A clients.
  • /.well-known/agent-card — A2A agent-card discovery.
  • /agentic_chat — AG-UI SSE endpoint, but backed directly by the ADK Runner (agui_endpoint.py), with a hardcoded _EVAL_USER_ID = "eval_user" for RAGAS evaluation.

The current AG-UI endpoint works but has two gaps that block it from being a production driver:

  1. Single user — every request collapses to eval_user; no per-browser session.
  2. No A2A surface — it bypasses the orchestrator's own A2A boundary, which means external A2A clients and the AG-UI client see different code paths and can drift.

2. Target architecture

┌────────────────────────────┐ ┌────────────────────────────────────┐ │ Next.js (browser) │ │ Orchestrator (port 8001) │ │ ─ CopilotChat / Sidebar │ │ │ │ ─ Generative UI cards │ │ ┌────────────────────────────┐ │ │ │ │ │ /agentic_chat (kept) │ │ │ /api/copilotkit ───────┐ │ │ │ Runner-backed, RAGAS use │ │ │ (Next route handler) │ │ │ └────────────────────────────┘ │ │ │ │ │ │ │ @copilotkit/runtime │ │ │ ┌────────────────────────────┐ │ │ HttpAgent ─────────┼──┼──SSE──┼─▶│ /a2a-agui ◀── NEW │ │ │ │ │ │ │ agui_bridge.py │ │ └─────────────────────────┘ │ │ │ • RunAgentInput → A2A │ │ │ │ │ • A2A events → AG-UI │ │ │ │ └──────────┬─────────────────┘ │ │ │ │ JSON-RPC (in-proc) │ │ │ ▼ │ │ │ ┌────────────────────────────┐ │ │ │ │ /a2a (existing) │ │ │ │ │ DefaultRequestHandler │ │ │ │ │ FinSightAgentExecutor │ │ │ │ └────────────────────────────┘ │ │ └────────────────────────────────────┘

Why route the AG-UI request through /a2a instead of calling the Runner directly? Three reasons:

  1. One canonical orchestration boundary. Whatever the orchestrator exposes externally (A2A) is exactly what the UI drives. No drift between "what an agent sees" and "what a human sees".
  2. Free reuse of A2A tasks & artifacts. Tasks already carry IDs, status, and structured artifacts — perfect for AG-UI's tool_call_* + state_* + message_* event families.
  3. Sub-agent observability for free. A2A events from the orchestrator already include sub-agent delegations as nested artifacts; the bridge can render each as a distinct ToolCallStart/Result pair.

3. Event translation table

The bridge consumes A2A events from the in-process JSON-RPC client and emits AG-UI events on the SSE stream. The mapping:

A2A eventAG-UI event(s) emittedNotes
(connection open)RUN_STARTEDEmit once per run_id.
TaskStatusUpdateEvent (state=working) with status messageSTEP_STARTED + STATE_DELTAStatus text → STATE_DELTA on key status; sub-agent name → step name.
TaskArtifactUpdateEvent (artifact type=function_call)TOOL_CALL_START + TOOL_CALL_ARGS + TOOL_CALL_ENDOne pair per sub-agent delegation or MCP tool call.
TaskArtifactUpdateEvent (artifact type=function_response)TOOL_CALL_RESULTMatch by tool_call_id kept in a per-run map.
TaskArtifactUpdateEvent (artifact type=text, delta=true)TEXT_MESSAGE_START (first) / TEXT_MESSAGE_CONTENT (deltas)Token streaming for the orchestrator's final synthesis.
TaskArtifactUpdateEvent (artifact type=investment_brief)STATE_SNAPSHOT (key=brief) + custom eventFinal structured InvestmentBrief JSON for generative UI.
TaskStatusUpdateEvent (state=completed)TEXT_MESSAGE_END + RUN_FINISHEDEnd of run.
TaskStatusUpdateEvent (state=failed)RUN_ERRORError string from task.status.error.

4. New module: agent_1_adk/agui_bridge.py

Replaces nothing; sits next to the existing agui_endpoint.py. Public surface:

def make_agui_bridge_endpoint(
    a2a_client_factory: Callable[[], A2AClient],
    *,
    session_store: SessionStore,        # see §5
) -> Callable[[Request], Awaitable[Response]]:
    """Return a Starlette POST handler for /a2a-agui that drives the
    orchestrator's A2A endpoint and streams AG-UI SSE."""

Internal pieces:

  • _A2AToAGUI — stateful translator; owns a per-run dict pending_calls: dict[str, str] and a per-run msg_id.
  • _emit(event_obj) -> str — same SSE framer as agui_endpoint._sse. Extract into shared/agui_sse.py as a tiny utility so both endpoints share it.
  • _extract_user_text(payload: RunAgentInput) -> str — copy from agui_endpoint; same logic.
  • _resolve_session(thread_id, run_id, payload) -> SessionHandle — see §5.

5. Session & memory continuity

This is the hardest part of feature parity. adk web gets sessions for free via DatabaseSessionService (sqlite at ./db/adk_sessions.db). The new bridge must reuse the same store so a user can switch between adk web and the new UI and see the same history.

AG-UI conceptFinSight conceptMapping
thread_idADK session_id1:1. New thread → new session row in adk_sessions.db.
run_idA2A task_idEach AG-UI run → one A2A task on the orchestrator.
User identityADK user_idFrom CopilotKit's properties.user_id (set by Next.js auth or anonymous cookie). Never fall back to eval_user.
Long-term memorySQLiteMemoryService (finsight://)The bridge doesn't touch memory directly; the orchestrator's _persist_memory_callback already fires per-turn and writes to the same DB.
Ticker memoryTickerMemoryRead-only side-channel — exposed to the UI via a separate GET /memory/ticker/{symbol} route, rendered in a sidebar.

Concretely, _resolve_session looks up the (app_name, user_id, thread_id) tuple via the same DatabaseSessionService instance the orchestrator already constructs in main.py. Inject it into make_agui_bridge_endpoint via closure rather than re-constructing.

6. Trace propagation + Langfuse

The orchestrator already injects W3C traceparent via shared/trace_context.py on every A2A task string. The bridge should:

  1. Start a new OTel span agui.run on each incoming POST.
  2. Stamp thread_id, run_id, user_id, session_id as span attributes.
  3. Pass the span context down so the orchestrator's internal A2A call inherits it (the existing trace_context helper already does this when called from inside a span).
  4. Emit one Langfuse-visible trace per AG-UI run — so the UI can deep-link to it.

Deep-link UI hook: after RUN_FINISHED, emit a final CUSTOM event with {type: "langfuse_trace", url: "..."} so a "View trace" chip can appear under each completed brief.

7. Step-by-step implementation

7.1 — Extract shared SSE helper tier 0

~20 min

  1. Create shared/agui_sse.py with sse(event) -> str.
  2. Replace _sse in agui_endpoint.py with the import.
  3. Verify the RAGAS eval still passes by running python -m pytest tests/evaluation/ -k agui -q.

7.2 — Scaffold bridge module tier 1

~1–2 hrs

  1. New file agent_1_adk/agui_bridge.py following the surface in §4.
  2. Internal A2A client: reuse a2a.client.ClientFactory pointed at http://{HOST}:{PORT}/a2a. Even though same-process, going over HTTP is the cleanest guarantee that the AG-UI and external A2A paths are identical.
  3. Implement the translator per the table in §3. Use a small dataclass RunCtx to hold per-run state (msg_id, pending_calls, text_started).

7.3 — Wire route in main.py tier 0

~15 min

from .agui_bridge import make_agui_bridge_endpoint

routes.append(Route(
    "/a2a-agui",
    make_agui_bridge_endpoint(
        a2a_client_factory=lambda: build_local_a2a_client(HOST, PORT),
        session_store=session_service,
    ),
    methods=["POST"],
))

7.4 — Memory sidebar route tier 1

~1 hr

  1. Add GET /memory/ticker/{symbol} backed by TickerMemory.get(symbol).
  2. Add GET /sessions?user_id=... backed by DatabaseSessionService.list_sessions.
  3. Add GET /sessions/{session_id}/events returning the event trace as a JSON array — used for the session-replay tab.

7.5 — User identity tier 1

~1 hr

  1. Read X-FinSight-User-Id header from the request (set by Next.js).
  2. If absent and CopilotKit's properties.user_id is in the payload, use that.
  3. If still absent, mint an anonymous anon-{uuid4} and return it in the response headers; the Next.js client stores it in a cookie.
  4. Never default to eval_user — that ID is reserved for RAGAS-batch usage on /agentic_chat.

7.6 — Cancellation tier 2

~½ day

AG-UI clients (CopilotKit's Stop button) close the SSE connection. The bridge must propagate that as A2A cancelTask JSON-RPC on the same run. Wire via Request.is_disconnected() polling in the streaming generator.

8. Backend test plan

  • Unit — tests/agui_bridge/test_translator.py: feed recorded A2A event sequences; assert the AG-UI event stream matches a golden file.
  • Integration — tests/agui_bridge/test_e2e.py: spin up the orchestrator on a random port, POST a real RunAgentInput, collect the SSE stream, assert it ends with RUN_FINISHED and contains at least one TOOL_CALL_START per sub-agent.
  • Parity — tests/agui_bridge/test_parity.py: send the same query to adk web's session store and to /a2a-agui; assert both produce the same final session row in adk_sessions.db.

12. "Killer" features — generative UI

This is where the new UI surpasses adk web rather than just matching it. Each item uses CopilotKit's useCoAgentStateRender / useCopilotAction hooks to render rich React components inline in the chat when specific AG-UI events arrive.

12.1 — Live sub-agent "thinking" tiles

While the orchestrator delegates to RAG / Quant / Sentiment, render three tiles (one per sub-agent) showing animated status. As each sub-agent finishes, its tile flips to show a one-sentence summary + a chevron to expand the full artifact.

┌─────────────────────────────┐ ┌─────────────────────────────┐ ┌─────────────────────────────┐ │ ● RAG (LlamaIndex) │ │ ● Quant (LangGraph) │ │ ● Sentiment (CrewAI) │ │ indexing 12 SEC filings… │ │ running DCF + stress… │ │ 45 news articles fetched │ │ ▓▓▓▓▓▓▓░░ 72% │ │ ▓▓▓▓▓░░░░░ 48% │ │ ▓▓▓▓▓▓▓▓▓▓ 100% ✓ │ └─────────────────────────────┘ └─────────────────────────────┘ └─────────────────────────────┘

12.2 — Investment Brief card (structured)

When the final investment_brief artifact arrives, replace the trailing text with a structured card: BUY/HOLD/SELL chip, confidence meter, key catalysts & risks as columns, a citations list with clickable filing links, and a DCF/Sharpe/VaR mini-panel.

12.3 — Inline price chart

Anywhere a ticker symbol appears in the assistant text, autolink to an inline TradingView Lightweight Chart popover (last 6 months, daily candles). Cached client-side via the existing get_prices MCP tool through a Next.js edge function.

12.4 — Portfolio-aware suggestions

User's portfolio (Zustand store, persisted in localStorage) is sent on every run as RunAgentInput.context. The orchestrator can use it to phrase recommendations relative to existing holdings ("you're already 18% NVDA — adding more crosses your concentration limit"). UI shows a "Portfolio context attached" pill.

12.5 — Memory timeline sidebar

For the current ticker, show a right-side timeline of past briefs from TickerMemory: date, recommendation, confidence, outcome (from PerformanceTracker). Click → load the historical brief into a read-only panel.

12.6 — "What changed?" diffing

When the same ticker is queried again, the UI diffs the new brief against the last stored one: new catalysts, risks that resolved, DCF delta, sentiment swing. Powered by a small client-side diff against the previous InvestmentBrief JSON.

12.7 — Trace deep-link

Every completed brief gets a "Open in Langfuse" chip in the trace drawer footer, linking to the trace URL emitted by the bridge (§6).

13. Human-in-the-loop checkpoints

CopilotKit exposes renderAndWaitForResponse on useCopilotAction. Use it to gate three orchestrator behaviors:

  1. Before SELL recommendations on held positions — modal: "Confirm SELL? You currently hold 142 shares @ avg $487. Tax impact: …" The orchestrator emits a tool_call named confirm_sell that the UI intercepts; user accept/reject is returned as the tool result.
  2. Before large external fetches — if the orchestrator requests >10 SEC filings or full-text search, ask the user to approve (cost & latency).
  3. Before writing to memory — show the brief snapshot that's about to be persisted; user can edit notes before save.

16. Frontend test plan

  • Component — Vitest + React Testing Library for each generative component, fed fixtures from shared/models.py via Zod schemas.
  • SSE integration — Playwright spec that POSTs through /api/copilotkit, waits for streamed tokens, and asserts the Trace drawer contains a row per sub-agent.

  • Visual regression — Storybook + Chromatic on the generative components.

Risks & open questions

RiskMitigation
A2A event surface doesn't carry sub-agent metadata cleanly (tool name is the only signal)Define a small artifact convention: every sub-agent delegation tags its artifact with metadata.agent_id and metadata.agent_color. Cheap orchestrator-side change.
Double event delivery if the bridge keeps the Runner-backed endpoint in parallelDifferent routes, different code paths. UI never points at /agentic_chat.
CopilotKit's runtime expects specific event names; FinSight emits some custom onesCustom events go through CopilotKit's "raw event" escape hatch (onRawEvent). Documented in the runtime adapter.
Session DB write contention between adk web and the new bridgeThe SQLite long-lived connection + write lock from improvement #3 already shipped. No further change needed.
LM Studio response latency makes "live" generative UI feel slowSub-agent tiles + STATE_DELTA give the user visible progress in <500ms even before any token arrives.
Hardcoded localhost:8001 in Next.jsPlumb through NEXT_PUBLIC_ORCHESTRATOR_URL; run_adk_web.bat sets it.

Open questions

  1. Authentication scope — is anonymous-cookie identity enough for v1, or do we need NextAuth from the start? Recommendation: anon-cookie first, NextAuth in F5.
  2. Do we want the new UI to replace adk web in run_adk_web.bat, or run alongside it on a separate port? Recommendation: alongside (port 3000) during F1–F4, replace in F5 once parity tests pass.
  3. Should the bridge stream memory recall events as first-class AG-UI events, or only as side-band JSON? Recommendation: first-class custom events — it's the highest-value differentiator vs. adk web.
