Sequenced rollout for RAG news ingestion, Sentiment agent redesign, Quant analytical depth, and end-to-end latency reduction.

A single source of truth that merges four independent proposals — RAG Improvement, Agent Responsibility Redesign, Quant Enhancement, and Latency Optimization — into one phased plan with explicit dependencies. The four source docs remain in this directory for reference, but this is the doc to follow during implementation.

2.2 Architectural defects

  • News is structurally orphaned. The RAG agent ingests SEC filings only; the Sentiment agent fetches news, runs VADER, and discards it. The retrieval-capable agent has no news; the news-fetching agent has no retrieval.
  • Agents fire sequentially. The orchestrator LLM emits one send_message at a time, serializing RAG → Quant → Sentiment for ~33s when asyncio.gather would give ~15s.
  • MCP connections are rebuilt per request. SSE connect + tool discovery costs 1–2s × 3 agents = 3–6s of pure overhead per query.
  • The DCF model is one-size-fits-all. 8% growth, 2.5% terminal, 10% WACC — for every ticker. Systematically wrong for growth and decline stocks alike.
  • Quant runs zero technical analysis. 5 years of OHLCV are loaded for Sharpe / vol / beta only. No RSI, MACD, MAs, trend classification.
  • Signal voting is a coin-flip. 4 unweighted signals, confidence formula clusters around 0.5, no calibration.
  • Sentiment agent currently overlaps RAG. Today it fetches news + filings and writes a narrative — exactly what RAG will own after Phase 1. The fix is not to delete the agent but to repurpose it for the context lane that no other agent covers: top-down macro regime + sideways peer landscape.

4. Why the order matters

Three hard dependencies dictate the sequencing:

  1. RAG must own news before Sentiment is rebranded. Today the Sentiment agent is the only thing pulling news into ChromaDB context. Phase 1 lands RAG news ingestion, so by Phase 3 the system still has news coverage even though Sentiment stops fetching news (it now fetches macro + peer data instead).
  2. Quant's fundamentals must land before signal voting is rewritten. The new weighted voting in format_output references fundamental and technical signals. Those nodes must exist first. Phase 1 lands the analytical nodes; later signal-voting work depends on them.
  3. Persistent MCP connections must land before background ingestion. The fire-and-forget filing ingestion (Phase 2 latency fix) assumes a long-lived MCP session. Without persistent connections, the background task would have to reconnect, defeating the latency win.

Two soft dependencies worth noting:

  • Parallel agent dispatch (Phase 2) becomes more valuable once each agent does more work (Phase 1 added analytical nodes), because the serial cost would otherwise grow.
  • The semantic-cache fix (Phase 4) is most useful after the pipeline is fast enough that users actually iterate on queries — i.e. after Phase 2.

    session = self._sessions.get(server_name)

        try:

12. Risks & open questions

12.1 Risks

  • Qwen3 parallel tool calling consistency. Qwen3-30B-A3B-2507 supports parallel tool calling natively, but the model may still serialize when the prompt is ambiguous or when one tool description hints at a sequencing constraint. Mitigation: explicit directive in the static preamble ("emit ALL send_message calls in ONE response"), plus a unit test asserting concurrent dispatch. If regressions appear, Option B (deterministic ticker-extraction shortcut, ~5h) is the documented fallback.
  • Multi-ticker queries. "Compare NVDA and AMD" requires the model to emit 6 parallel send_message calls (3 agents × 2 tickers). Qwen handles this in principle but it should be validated against the eval set; the synthesis prompt also needs to merge results per-ticker rather than treating them as one bag.
  • Background ingestion gives partial first responses. The first query for a new ticker may return before filings are indexed. UX must signal "data is loading" or the follow-up query will look magically better. Consider a small note in the response when the index is incomplete.
  • Form 4 parsing is brittle. SEC XML formats drift. The insider signal node should fail soft — emit "no insider data" rather than crash the agent.
  • Hybrid search increases memory footprint. CrossEncoder rerank loads a model into the RAG agent process. Validate against the deployment env's RAM budget.
  • RAGAS runtime eval competes for LLM bandwidth. Confirmed from logs/sentiment.log and logs/rag_agent.log: after every RAG/Sentiment response, 3-5 RAGAS metrics fire LLM calls against the same Qwen3-30B that the live agents use. On a model-eviction event, every in-flight metric retries 3× and the eval can run 1-5 minutes after the response — actively slowing the next user query. The §8.5.12 fixes (separate eval model, circuit breaker, max_retries=1, kill-switch) are needed even if the rest of Phase 4 is deferred.

12.2 Open questions

  1. For multi-ticker comparisons, should the orchestrator synthesis prompt force the model to produce per-ticker briefs then a comparison summary, or one merged brief? Affects how parallel dispatch results are formatted before the final LLM call.
  2. Peer-set selection: hand-curated map (current plan in §7.4.2 and §8.5.5), SIC-code lookup, or sector-ETF holdings? The hand-curated map is the cheapest path but stays stale unless reviewed quarterly. Shared between Sentiment (Market Context) and Quant (peer rank), so the choice should be made once.
  3. Should the semantic cache be per-user or global? Per-user is cleaner but loses hit-rate on popular tickers.
  4. Market Context narrative depends on having a valid peer set. What's the fallback when get_peer_tickers returns empty (unknown industry)? Options: (a) crew narrates macro-only and notes "no peer comparison available", or (b) crew falls back to a generic "large-cap US equities" peer set. Decide before Phase 3 lands.
  5. Risk new in this revision: the macro narrative may overweight transient indicator moves (e.g. one bad VIX day). Consider asking the crew to reference 5-day percent changes (already provided by get_macro_indicators) rather than spot values.
